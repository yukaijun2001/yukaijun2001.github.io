# 1.准备数据

论文、PDF、Word、网页、数据库、企业文档、FAQ、代码文档、实验记录

# 2.文档分析

把原始文件转换成纯文本或结构化文本。

pdf、word→文本

网页html→正文

表格 → 行列文本

代码 → 函数、注释、说明文本


💡

分析工具：mineru、paddleocr



# 3.切分

方式：字数、段落、章节、页码

常见的分块策略有六种：自然结构分块、固定大小分块、滑动窗口分块、递归分块、语义分块和混合分块。
1）自然结构分块：按文档原有格式拆分，遇到标题、空行、章节编号、句号这些天然分隔符就切一刀。Markdown文档按###切、普通文档按段落空行切。
2）固定大小分块：不管内容是什么，按固定字符数、词数或token数均匀切。比如每500tokens切一块，简单粗暴，适合快速处理大量非结构化文本。
3）滑动窗口分块：在固定大小基础上加了重叠机制。相邻两个块之间保留10%到20%的重叠内容，避免关键信息刚好卡在分界线上被截断。
4）递归分块：分层拆分，先按大结构粗分，超长的部分再递归细化。比如先按章节切，章节太长就按段落切，段落还长就按句子切，直到块大小达标。
5）语义分块：用NLP模型判断语义边界，确保每个块是完整的语义单元。不是机械按字数切，而是让模型识别”这段话讲完了，下一段是新话题”的位置。
6）混合分块：把上面几种策略组合起来用。先固定分块快速处理，再对关键部分做语义优化，类似粗筛加精修的思路。


💡

提问：实际项目中怎么选择分块策略？
回答：看文档类型和业务需求。结构化文档比如技术文档、法律合同，优先自然结构分块，能保证章节完整。非结构化文本比如网页、聊天记录，用固定大小加滑动窗口，简单高效。
对检索精度要求特别高的场景，比如医疗问答、金融分析，上语义分块。生产环境一般是混合策略，先结构分块粗筛，再语义分块精修。

提问：分块大小和重叠比例怎么调优？
回答：没有银弹，得根据检索效果迭代。起点一般是300到500tokens，重叠10%到20%。然后跑一批测试query，看召回率和答案质量。召回的块经常不完整，说明块太小或重
叠太少。召回的块经常混入无关内容，说明块太大。不同类型文档最优参数不一样，FAQ类要细，长文章类要粗，最好分类型配置。

提问：语义分块的计算成本怎么控制？
回答：全量语义分块确实贵，每对相邻句子都要过embedding 模型算相似度。优化思路有几个：一是用轻量模型，比如 all-MiniLM-L6-v2 比 BERT-large快很多但效果够用。二是
先粗分再精分，用固定分块快速切成大块，只对大块内部做语义细分。三是缓存，同一份文档分块结果存起来，不用每次重算。四是设相似度阀值，连续几个句子相似度都高就直接合
并，不用逐句计算。

# 5.存入向量数据库

把每个 chunk 的内容和对应向量存入向量数据库。

常见向量数据库包括：

FAISS、Milvus、Chroma、Weaviate、Pinecone、Qdrant 等。


💡

提问：余弦相似度和欧氏距离有什么区别？RAG里一般用哪个？
回答：余弦相似度只看方向不看长度，两个向量夹角越小相似度越高，跟向量本身多长没关系。欧氏距离是点到点的直线距离，既看方向也看长度。RAG里一般用余弦相似度，因为
Embedding向量的长度没有明确的语义含义，我们只关心方向。两段话说的是不是同一件事，跟向量长度没关系。不过很多向量数据库会把向量归一化，归一化之后余弦相似度和欧
氏距离的排序结果是一样的。
提问：Embedding向量维度一般多少？维度高低有什么影响?
回答：常见的维度从 384 到 3072 不等。all-MiniLM-L6-v2 是 384 维，OpenAl text-embedding-3-small是 1536 维，text-embedding-3-large 是 3072 维。维度越高，能表达
的语义信息越丰富，检索精度越高，但存储和计算成本也越高。十亿级向量，384维和1536维的存储差4倍，检索延迟也会增加。实际选择要平衡精度和成本，大多数场景384到
768 维够用，对精度要求特别高的再上1536。
提问：用户问题和文档块用同一个模型生成Embedding吗?
回答：一般用同一个模型。问题和文档在同一个向量空间里才能比较相似度。有些场景会用双塔模型，问题和文档分别过不同的编码器，但最后映射到同一个空间。还有一种做法是对
问题做扩展，比如用大模型把问题改写成多个版本，每个版本分别检索再合并结果，这叫queryexpansion。核心原则是问题和文档的Embedding要在同一个语义空间里可比较。

↓(依靠embedding模型)
[0.18, -0.09, 0.61, ...]
> 


💡

查询扩展：

常见的扩展方式有三种:
1)基于规则的扩展:维护一份同义词词典，“减肥“对应”瘦身、控制体重、减脂”。简单粗暴，适合垂直领域
2)基于LLM的扩展:让大模型直接改写查询，效果最好但有延迟和成本。




💡

提问:用大模型做查询扩展会增加延迟，有没有什么办法优化?
回答:几个常用的优化手段:
1)用小模型做扩展
2)扩展结果做缓存，同样的查询不重复调模型
3)异步扩展，原始查询先跑一路检索，扩展查询同时在跑，两路结果合并
4)热门查询预扩展，把高频问题的扩展结果提前算好存起来
提问:查询扩展和混合检索有什么关系?能配合使用吗?
回答:充全可以配台。查询扩展解决的是”查询词不准”的问题，混合检索解决的是”检索方式单一的问题，扩展后的查询既可以跑向呈检索抓语义相关的，也可以跑BM25抓关健问精
确匹配的，两路结果用RRF融合。这样既覆盖了同义词，又兼顾了语义和精确匹配，召回效果最好。




💡

> 自查询工作流程
> 

自查询发生在用户输入到检索文档之间的意图解析阶段，整个流程分这么几步:
用户输入一个查询后，系统先判断要不要做自查询。如果用户问得很明确，直接争原始查询去检索就行。如果用户表述模糊、带隐含条件，就进入意图解折环节，让LLM 把自然语言拆成语义关键词和元数据过滤条件，生成结构化查询。然后拿着这个结构化查询去向量库做检索，结合元数据过滤筛选文档，最后排序后送给生成模型出答案。

# 7.检索相关片段（召回）

系统从知识库中找出与问题最相关的 Top-K 个 chunk

embedding模型只做文档——>向量，不进行检索。检索需要向量数据库内置的算法（如下）：

## 算法

- 余弦相似度

    公式：对于两个 n 维向量 $A = (a_1, a_2, \dots, a_n)$ 和 $B = (b_1, b_2, \dots, b_n)$

    $$
    \mathrm{Similarity}(A, B)=\cos(\theta)=\frac{A \cdot B}{\|A\|\|B\|}
    $$

    展开后：

    $$
    \cos(\theta)=\frac{\sum_{i=1}^{n} a_i b_i}{\sqrt{\sum_{i=1}^{n} a_i^2} \cdot \sqrt{\sum_{i=1}^{n} b_i^2}}
    $$

- 欧式距离

    公式：对于两个 n 维向量 $A = (a_1, a_2, \dots, a_n)$ 和 $B = (b_1, b_2, \dots, b_n)$

    $$
    d(A, B)=\sqrt{\sum_{i=1}^{n}\left(a_i-b_i\right)^2}
    $$

- 点积

    公式：

    $$
    A \cdot B=\|A\|\|B\| \cos(\theta)
    $$
    


💡

混合检索：向量检索+关键词检索。融合用：RRF算法

关键词检索：BM25算法



# 8.重排序

初步检索出来的结果不一定最准确，所以可以再用 rerank 模型重新排序。

例如原始检索结果是：

```
A, B, C, D, E
```

rerank 后可能变成：

```
C, A, E, B, D
```

这样可以把真正有用的内容排到前面。

# 10.大模型生成回复

大模型基于检索到的资料生成回答，而不是单纯依靠自身记忆。

这就是 RAG 的核心：

```
用户问题 + 检索资料 → 大模型 → 最终答案
```

# 面试提问

提问：Rerank 的延迟一般有多少？对整体 RAG 系统性能影响大吗？

回答：Cross-Encoder 的 Rerank 延迟通常在 50-200ms 左右，具体取决于模型大小和候选文档数量。如果召回 100 个文档，每个文档平均 500 tokens，用 bge-reranker-base 在 GPU 上跑大概 100ms 左右。对整体 RAG 系统来说，向量检索通常只要 10-50ms，Rerank 这一步反而成了瓶颈。所以要控制召回数量，一般 50-100 个就够了，不要贪多。

提问：除了 Cross-Encoder，还有什么其他 Rerank 方案？

回答：有几种。一是用 ColBERT 这类延迟交互模型，它把 Document 的 token 级向量提前算好，Query 来了只需要做 token 级别的相似度匹配，比 Cross-Encoder 快很多但精度接近。二是用 LLM 直接做 Rerank，把候选文档和 Query 喂进去让它打分，效果好但成本高。三是基于规则的 Rerank，比如优先最近更新的文档、优先特定来源的文档，简单场景够用。

提问：如果 Rerank 模型和 Embedding 模型对同一个文档的打分差异很大，应该信谁？

回答：信 Rerank。Embedding 模型用的是 Bi-Encoder 架构，Query 和 Document 没有直接交互，只是各自编码后算相似度，语义理解比较浅。Rerank 的 Cross-Encoder 是把 Query 和 Document 拼一起过 Transformer，有充分的注意力交互，对语义匹配的判断更准。Embedding 负责快速召回，Rerank 负责精准排序，分工明确。
